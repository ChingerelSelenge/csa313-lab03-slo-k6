## Хийсэн ажил

`server.js`-д гурван endpoint-той локал API (`/cart/add`, `/report`, `/pay`) босгож, тус бүрд чанарын сценарио бичээд, SLO болгож, `slo-test.js`-д k6 threshold болгож кодчиллоо. 

---

## Сценарио 1: Performance — /cart/add хариу хугацаа

1. **Тойм:** `/cart/add` endpoint хэвийн ачаалалд хурдан хариулах ёстой.
2. **Системийн төлөв:** Систем хэвийн ажиллаж байгаа, унтраагаагүй.
3. **Орчны төлөв:** 20 VU тогтмол ачаалал, сүлжээ хэвийн.
4. **Гадаад өдөөлт:** Хэрэглэгч сагсанд бараа нэмэх хүсэлт илгээв.
5. **Шаардлагатай хариу:** Систем 200 OK хариу буцаана.
6. **Хэмжүүр:** p95 хариу хугацаа < 5мс, 20 VU-д, 1 минут.

## Сценарио 2: Reliability — /pay эвдрэлийн давтамж

1. **Тойм:** `/pay` endpoint-ийн эвдрэлийн давтамж хэрэглэгчийн итгэлд шууд нөлөөлдөг.
2. **Системийн төлөв:** Систем хэвийн ажиллаж байгаа.
3. **Орчны төлөв:** 20 VU тогтмол ачаалал, 1 минут.
4. **Гадаад өдөөлт:** Хэрэглэгч төлбөрийн үйлдэл гүйцэтгэв.
5. **Шаардлагатай хариу:** Систем 200 OK хариу буцаах ёстой; алдааны хувь тодорхой хязгаараас хэтрэхгүй.
6. **Хэмжүүр:** error rate < 8%, 20 VU-д, 1 минут.

## Сценарио 3: Availability — серверийн эвдрэл ба сэргэлт

1. **Тойм:** Сервер гэнэт зогсоход систем ерөнхийдөө хэр найдвартай хариу үйлдэл үзүүлэх вэ.
2. **Системийн төлөв:** Сервер ажиллаж байгаад гэнэт зогссон.
3. **Орчны төлөв:** 10 VU-с 20 VU хүртэл ачаалал, 2 минутын цонх.
4. **Гадаад өдөөлт:** Сервер 10 секундийн турш ЭВДРЭЛД орсон (унасан), дараа нь дахин асаагдсан.
5. **Шаардлагатай хариу:** Систем сэргэсний дараа хэвийн ажиллагаандаа буцах ёстой.
6. **Хэмжүүр:** availability хувь ≥ 90%, сэргэх хугацаа ~10 секунд.

## SLO хүснэгт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency | p95 < 5мс | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | `/pay` error rate | < 8% | 1 мин, 20 VU |
| Availability | бүх хүсэлтийн амжилтын хувь (checks) | ≥ 90% | 2 мин, 10с зогсолт орсон |
| (Нэмэлт) Performance | `/report` latency | p95 < 450мс | 20 VU тогтмол ачаалалд, 1 мин |

**Босго сонгосон үндэслэл:**
- `/cart/add` p95 < 5мс — localhost дээр анхны туршилтаар бодит p95 ~2.46мс байсан тул 200мс гэдэг сул босго байх байсан, иймд бодит гүйцэтгэлдээ ойрхон, утга учиртай босго болгож 5мс болгосон.
- `/pay` error rate < 8% — серверт зориудаар ~5% алдаа суулгасан (`Math.random() < 0.05`) тул 8% нь бодитой, бага зэрэг хөвөгч зайтай босго.
- Availability ≥ 90% — 2 минутын турш 10 секундийн зогсолт орсныг тэсвэрлэх боломжтой түвшин гэж үзсэн.
- `/report` p95 < 450мс — сервер 200-400мс хооронд санамсаргүй хүлээдэг тул хамгийн муу тохиолдол дээр бага зэрэг зай үлдээж 450мс болгосон.

**Error budget тооцоо (цагаар):**
```
2 минутын цонхонд 90% availability = 12 секундийн "эвдрэх эрх"
(2 мин = 120с, 10% × 120с = 12с)
```

## Chaos туршилт — results/chaos.txt

`slo-test.js`-ийн `duration`-ыг `2m` болгож ажиллуулаад, ~21-р секундэд серверийг зогсоож, дараа нь дахин асаав (лог дээр `connect: connection refused` алдаанууд ойролцоогоор 20-44-р секундүүдэд, ~24 секундийн турш үргэлжилсэн байна):

| Threshold | Босго | Бодит утга | Үр дүн |
|---|---|---|---|
| `checks` (availability) | rate > 0.90 | **89.10%** | ✗ **FAIL** |
| `http_req_duration{name:cart}` | p(95) < 5мс | 3.12мс | ✓ PASS |
| `http_req_duration{name:report}` | p(95) < 450мс | 391.8мс | ✓ PASS |
| `http_req_failed{name:pay}` | rate < 0.08 | **14.56%** | ✗ **FAIL** |

Нийт 5643 HTTP хүсэлт (2м01.3с ажиллав), үүнээс 615 (10.89%) амжилтгүй болсон. `checks` нийт 5643-аас 5028 амжилттай (89.10%), 615 амжилтгүй (10.89%). Endpoint тус бүрээр: cart 1715✓/166✗ (91%), report 1706✓/175✗ (90%), pay 1607✓/274✗ (85%, `/pay`-д зориулсан threshold дээр 14.56% error rate).

Console дэвсгэрт харагдсан эцсийн алдаа:
```
level=error msg="thresholds on metrics 'checks, http_req_failed{name:pay}' have been crossed"
```

**Availability threshold: ✗ FAIL** (89.10% < 90% босго)
**Reliability threshold (`http_req_failed{name:pay}`): ✗ FAIL** (14.56% > 8% босго)

**Бодит availability (хүсэлтээр тооцсон):**
```
availability = амжилттай checks / нийт checks = 5028 / 5643 = 89.10%
```
(`http_req_failed`-ээр тооцоход ч ойролцоо утга: 100% − 10.89% = 89.11% — хоёр аргаар тооцсон нь бараг давхцаж байна.)

**Яагаад цагаар тооцсон 12 секундийн budget ба хүсэлтээр тооцсон утга зөрдөг вэ:**

Цагаар: сервер ~10 секунд зогссон, нийт 121.3 секундийн турш ажилласан тул зогсолт нь **121.3с-ийн 8.24%**-ийг эзэлж байна — энэ нь миний тохируулсан 10%-ийн time-budget-аас **бага** тул цагаар харвал budget хэтрээгүй мэт харагдана.

Гэтэл бодит хүсэлтээр тооцоход алдааны хувь **10.89%** гарсан — өөрөөр хэлбэл time-budget-аас **их**. Шалтгаан нь: сервер хэвийн ажиллаж байхад `/report` endpoint дунджаар ~276-390мс хүлээдэг тул секунд тутамд цөөн хүсэлт л боловсруулагддаг. Харин сервер унасан үед (`connection refused`) хүсэлт **процесс хийлгэхгүйгээр агшин зуур** (0-1мс дотор) буцдаг тул зогсолтын секунд бүрд, хэвийн ажиллаж байсан үеийнхээс хамаагүй **олон** хүсэлт "багтаж" амжилтгүй болдог. Иймд зогсолтын 10 секунд бодит цагаараа тооцсоноос хамаагүй **олон хувийг** нийт хүсэлтийн тооноос "иддэг" — 8.24% цагийн зогсолт → 10.89% хүсэлтийн алдаа руу хөрвүүлэгдсэн нь яг энэ шалтгаанаас болсон.

**Reliability SLO мөн зөрчигдсөн үү:**

Тийм, `http_req_failed{name:pay}` мөн FAIL болсон (14.56% > 8%). Учир нь сервер унасан үед `/pay`-ийн хүсэлт бүр л амжилтгүй болдог — нэг эвдрэл (crash) нэг дор availability, reliability гэсэн хоёр SLO-г зэрэг зөрчдөг. Хоёр SLI-г бие даан хянахын тулд `/pay`-ийн алдааг зөвхөн serverr-ийн бизнес-логикоос (жишээ: `Math.random()<0.05` санамсаргүй алдаа) үүссэн 5xx-ийг тоолж, харин `connection refused`/timeout шалтгаантай алдааг тусад нь ангилж, зөвхөн availability SLI-д тооцох хэрэгтэй.
